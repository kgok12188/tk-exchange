## 现货结算持久化设计（含资金划转）

本文只关注 **现货交易 + 无手续费** 的最小持久化集合，并在此基础上**保留资金划转流水**。撮合逻辑、合约持仓等不在本文范围内。

### 1. 持久化目标

trading-server 在内存中维护 `UserTradingBook`（账户 + 订单 + 成交视图），通过 `AsyncMessageItem` 写入 `trading_result_(shard)`，由 `trading_result_sync` 落库。  
在「现货 + 无手续费」前提下，最小需要落库的表/实体为：

- **账户**：`account`
- **订单**：`co_order`（作为通用订单表，但只使用现货相关字段）
- **成交记录**：`trade_order`
- **资金划转流水**：`transfer`

其它表（如 `co_position`）可以在纯现货场景下忽略。

同时，为了在全链路上统一「版本/顺序」与「业务主键」，本设计约定：

- `trading_(分片)` Kafka topic **仅一个分区**；
- **订单主键 `order.id` 与版本号 `txid` 都基于 Kafka offset 构造**：
  - **`order.id` = `trading_(分片)` Kafka offset 与分片 id（最多 128 分片）在 `long` 的后 63 位上按位组合得到的唯一值**；
  - **`txid` = 该条 `trading_(分片)` 消息的 Kafka offset**（不含分片 id 部分），便于按 offset 对账与重放；
  - open-api 层的**批量下单会被转换为多条「单笔下单」消息**写入 `trading_(分片)`，因此不需要在一个 offset 内支持多笔订单主键。

### 2. 表结构概览（现有表的简化使用方式）

#### 2.1 账户：`account`

- **用途**：记录每个用户在每个币种上的余额。
- **Key 字段**：
  - `uid`：用户 ID
  - `coin_id` / `coin_name`：币种标识
  - `available_balance`：可用余额
  - `order_frozen`：挂单冻结资金（现货可选）
  - `txid`：版本号 / 乐观锁

#### 2.2 订单：`co_order`

- **用途**：记录用户委托单生命周期（NEW / PARTIAL_FILLED / FILLED / CANCELED / PARTIAL_CANCELED / REJECTED）。
- **Key 字段**（现货场景下关注）：
  - `id`：订单 ID
  - `uid`：用户 ID
  - `symbol`：交易对（如 BTC-USDT）
  - `market_id`：交易对 ID
  - `amount` / `volume`：下单总金额或总数量
  - `price_type`：价格类型（LIMIT / MARKET）
  - `price`：委托价格（市价单可为参考价）
  - `status`：订单状态（0 初始化 1 部分成交 2 完全成交 3 部分成交撤销 4 撤销 5 异常）
  - `deal_volume` / `deal_amount` / `avg_deal_price`：成交进度
  - `ctime` / `mtime` / `completed_time` / `cancel_time`

#### 2.3 成交记录：`trade_order`

- **用途**：记录每一次撮合成交，方便对账/查询。
- **Key 字段**：
  - `id`：主键
  - `uid`：用户 ID
  - `match_id`：撮合 ID
  - `order_id`：对应订单 ID
  - `side`：买/卖
  - `price` / `volume`：成交价格与数量
  - `status`：处理状态（0 处理中 1 完成 2 失败）
  - `ctime` / `mtime`

> 在「无手续费」场景下，`fee` 字段可以总是写入 0。

#### 2.4 资金划转流水：`transfer`

- **用途**：记录资金转入/转出流水（如充值、提现、内部划转），与账户变动对应。
- **Key 字段**：
  - `id`：主键
  - `uid`：用户 ID
  - `transfer_id`：业务侧的唯一转账 ID
  - `coin_id`：币种 ID
  - `amount`：划转金额
  - `status`：0 进行中 1 成功 2 失败
  - `type`：0 转入 1 转出
  - `ctime` / `mtime`

### 3. 业务行为与持久化映射（现货 + 无手续费）

#### 3.1 下单（NEW_ORDER）

- **输入**：用户请求，包含 `uid`, `symbol`, `side`, `type`, `price`, `volume/amount` 等。
- **账户表 `account`**：
  - 若采用「挂单冻结」：
    - 买单：冻结计价币种（如 USDT）的 `order_frozen`，减少 `available_balance`。
    - 卖单：冻结基础币种（如 BTC）的 `order_frozen`，减少 `available_balance`。
  - 若暂不做冻结，可仅检查可用余额，暂不写入冻结字段。
- **订单表 `co_order`**：
  - 插入一行新记录，`status = 0`（初始化/未成交）。

#### 3.2 撮合成交（MATCH → TradingSettle → TradingServer）

- **输入**：`TradingSettle{ uid, finishOrders[], tickets[] }`
- **订单表 `co_order`**：
  - 对 `finishOrders` 中涉及的订单：
    - 更新 `status`、`deal_volume`、`deal_amount`、`avg_deal_price`。
    - 若订单进入终态（完全成交/撤单/部分成交撤单），更新 `completed_time` / `cancel_time`。
- **成交表 `trade_order`**：
  - 对每个 `Ticket`（或拆分后的成交腿）：
    - 插入一行成交记录，填充 `uid`, `order_id`, `match_id`, `side`, `price`, `volume`。
    - `fee` 写 0，`status` 置为已完成。
- **账户表 `account`**：
  - 买成交：
    - 计价币种（如 USDT）减少成交金额（price × volume），释放可能的多余冻结。
    - 基础币种（如 BTC）增加成交数量。
  - 卖成交：
    - 基础币种减少成交数量（释放冻结 + 扣减卖出部分）。
    - 计价币种增加成交金额。

#### 3.3 撤单（CANCEL_ORDER）

- **订单表 `co_order`**：
  - 将对应订单状态更新为撤单/部分成交撤单。
- **账户表 `account`**：
  - 释放该订单占用的 `order_frozen` 金额或数量，恢复到 `available_balance`。

#### 3.4 资金划转（TRANSFER）

- **transfer 表**：
  - 插入一行流水，记录 `uid`, `transfer_id`, `coin_id`, `amount`, `type`（转入/转出），`status`。
- **账户表 `account`**：
  - 对应币种的 `available_balance` 增加（转入）或减少（转出）。

---

### 4. 与 trading_result_(shard) 的关系

trading-server 不直接操作上述表，而是：

1. 在内存中根据 `TradingSettle` / 用户指令更新 `UserTradingBook`（Account + Order 视图）。
2. 把每次变更打包为一组「持久化批次」 AsyncMessageItem（`type = ACCOUNT / ORDER / TRADE_ORDER / TRANSFER`，`messages` 为同一类型下需要写库的记录列表），并为这批记录统一设置 `txid = trading_(shard)` 上本条消息的 Kafka offset。
3. 写入 `trading_result_(shard)`。
4. 由 `trading_result_sync` 消费 `trading_result_(shard)` 并调用 `PersistenceService.flush` 将变更写入：
   - `account`
   - `co_order`
   - `trade_order`
   - `transfer`
   并将 `AsyncMessageItem.txId` 映射到各表的 `txid` 字段（例如 `account.txid`、`co_order.txid`、`trade_order.txid`、`transfer.txid`），从而实现「同一条 trading_(shard) 消息产生的所有持久化记录拥有相同 txid（= offset）」。

本文档描述的是这些事件最终在数据库层面的映射和最小字段集合。
